## สรุป

พบช่องโหว่จริง **3 ข้อ (HIGH)** และข้อบกพร่องที่กระทบผู้ใช้ **3 ข้อ (MEDIUM)** ทั้งหมด
ยืนยันด้วยการยิงระบบที่รันอยู่ · แก้แล้ว 5 ข้อ (SEC-01, 02, 03, 06, 07) เหลือ SEC-05
ที่ต้องมีคำตัดสินก่อนแก้ · **SEC-04 ถูกถอน** — ผมวัดบนเครื่อง dev แล้วสรุปผิด (ดูข้างล่าง)

**สองข้อสุดท้ายมาจากการกวาดโค้ด ไม่ใช่การยิงสุ่ม** และทั้งคู่อยู่ในชั้นเดียวกัน: ระบบ

## 🟠 HIGH · SEC-01 · ตัวจำกัดอัตราถูกข้ามด้วยการเปลี่ยนพารามิเตอร์ใน URL

**ตำแหน่ง:** `apps/backend/middleware/rate-limiter.js:77`
**ปลายทางที่กระทบ:** ทุก endpoint ที่มีพารามิเตอร์ใน URL · ที่ร้ายที่สุดคือ
`GET /api/public/verify/:certificateNumber` (สาธารณะ ไม่ต้องล็อกอิน)

**ภัยคุกคาม:** กุญแจนับคือ `ratelimit:${ip}:${req.path}` ซึ่งรวม *ค่า* ของพารามิเตอร์
เข้าไปด้วย ทุกค่าที่ต่างกันจึงได้ถังนับของตัวเอง · ผู้โจมตีที่ไล่เดาเลขใบรับรอง
เปลี่ยนค่าไปเรื่อย ๆ จะไม่ถูกจำกัดเลย ซึ่งคือรูปแบบการโจมตีที่ limiter นี้ตั้งใจกันพอดี

คอมเมนต์ใน `routes/api/auth/public.js:28-29` เขียนว่า *"enumeration is no longer
practical"* เพราะเลขใบรับรองไม่เรียงลำดับ — จริง แต่ชั้นที่สองที่ควรกันไว้ไม่ทำงานเลย

**พิสูจน์ (ก่อนแก้):**
```
ยิงเลขเดิม 45 ครั้ง      ->  30 ผ่าน · 15 ถูกบล็อก (429)   limiter ทำงาน
ยิงเลขต่างกัน 45 ครั้ง   ->  45 ผ่านทั้งหมด                limiter ถูกข้าม
header ตอบ X-RateLimit-Remaining: 29 ทุกเลขใหม่ = ถังใหม่ทุกครั้ง
```

**แก้:** นับที่ *เส้นทาง* ไม่ใช่ *ค่าในเส้นทาง* — ถาม express ก่อน
(`req.baseUrl + req.route.path` = `/api/public/verify/:certificateNumber`) แล้วค่อย
ถอยไปเดาจากหน้าตาของ segment เมื่อ limiter ถูกแขวนระดับ app

```js
function routeKeyOf(req) {
  const declared = req.route && typeof req.route.path === 'string' ? req.route.path : null;
  if (declared) { return `${req.baseUrl || ''}${declared}`; }
  return fallbackPatternOf(req.path);
}
const key = customKey ? `ratelimit:${customKey}` : `ratelimit:${ip}:${routeKeyOf(req)}`;
```

**พิสูจน์ (หลังแก้):**
```
ยิงเลขต่างกัน 45 ครั้ง   ->  30 ผ่าน · 15 ถูกบล็อก
ยิงเลขสั้น A1..A40       ->  30 ผ่าน · 10 ถูกบล็อก
health / version / login ->  200 ทั้งหมด (เส้นทางอื่นยังมีถังของตัวเอง)
```

> การเดาด้วย heuristic อย่างเดียวไม่พอ — รอบแรกผมใช้ความยาว segment แล้วค่าสั้นอย่าง
> `A1` ยังลอด · เทสจับได้ก่อนขึ้น commit

## 🟡 MEDIUM · SEC-02 · 191 จาก 204 รหัสข้อผิดพลาดบอกผู้ใช้ว่า "ระบบพัง"

**ตำแหน่ง:** `apps/backend/shared/api-response.js` (`sendErrorResponse`)

`DEFAULT_ERROR_MESSAGES` รู้จัก 13 รหัส · ที่เหลือตกลงมาที่ `INTERNAL_SERVER_ERROR`
ทั้งหมด ทั้งที่ `shared/error-codes.js` มีประโยคไทยเขียนไว้ครบ 204 รหัส

**พิสูจน์:** ล็อกอินผิด 5 ครั้ง → ระบบล็อกบัญชี**ถูกต้อง** ตอบ `423 ACCOUNT_LOCKED`
แต่ `messageTh` = *"เกิดข้อผิดพลาดภายในระบบ"* ทั้งที่แคตตาล็อกมี
*"บัญชีถูกล็อกชั่วคราวเนื่องจากเข้าสู่ระบบผิดหลายครั้ง"*

**ทำไมเป็นเรื่องความปลอดภัย ไม่ใช่แค่ UX:** ผู้ใช้ที่ถูกบอกว่าระบบพังจะ**ลองซ้ำ ๆ**
แทนที่จะรอให้ครบเวลา — ซึ่งยืดการล็อกออกไปอีก และสร้างภาระให้ซัพพอร์ต

**แก้:** ลำดับการหาข้อความเป็น ผู้เรียก → แคตตาล็อก 204 รหัส → แคตตาล็อกเล็ก → ข้อความกลาง

## ~~🟡 MEDIUM · SEC-04 · ไม่มี Content-Security-Policy~~ — **ผมสรุปผิด แก้เมื่อ 2026-09-09**

ข้อความเดิม: "helmet ตั้ง X-Frame-Options, X-Content-Type-Options, HSTS,
Referrer-Policy ครบ แต่ไม่มี CSP"

**ที่ถูกคือ:** `server.js:150` เขียนว่า
`contentSecurityPolicy: exposesDebugSurfaces ? false : undefined` และ
`exposesDebugSurfaces` เป็นจริงเฉพาะเมื่อ `NODE_ENV` เป็น `development` หรือ `test`
(`server.js:100`) · `undefined` คือการปล่อยให้ helmet ใช้ CSP มาตรฐานของตัวเอง
**staging และ production จึงมี CSP อยู่แล้ว** ที่ไม่มีคือเครื่อง dev ซึ่งเป็นเจตนา

ผมวัดบนเครื่อง dev แล้วสรุปเป็นข้อบกพร่องของระบบ · ที่จับได้คือตอนอ่าน `server.js`
ในงานอีกข้อหนึ่ง (Step 3.1) ไม่ใช่จากการทดสอบ — headers ที่วัดบน dev ไม่ตอบคำถามว่า
production ตั้งอะไร

**สิ่งที่ยังไม่รู้จริง:** CSP มาตรฐานของ helmet เข้มพอสำหรับ Next หรือไม่ และหน้าจอ
พังตรงไหนบ้างเมื่อเปิด · ต้องวัดบน staging ไม่ใช่บนเครื่อง dev — ค้างเป็นงานที่ยัง
ไม่ได้ทำ ไม่ใช่ข้อบกพร่องที่ยืนยันแล้ว

## 🟠 HIGH · SEC-07 · เอกสารตอบข้อบกพร่องและภาพถ่ายการตรวจแปลง เปิดให้ผู้ใช้คนไหนก็ได้

**ตำแหน่ง:** `apps/backend/middleware/uploads-access.js:210` (`gateSlipObjectAccess`)

`classifyUploadsPath` จัด 5 ชนิดเป็นข้อมูลส่วนบุคคล — `root` (บัตรประชาชน/รูปประจำตัว),
`slip`, `draft`, `car`, `audit` — และประตูแรกบังคับให้ทั้ง 5 ต้องมีเซสชันได้ถูกต้อง
แต่ประตูที่สองซึ่งเป็นตัวถามว่า "เซสชันของใคร" ส่งเข้า ACL แค่ 2 ชนิด (`application-drafts/`,
`wizard-drafts/`) อีก 3 ชนิดจึงถูกป้องกันด้วยการเดาชื่อไฟล์ uuid เพียงอย่างเดียว

**วัดจริงก่อนแก้:**
```
GET /uploads/car/secret.txt   ไม่มีโทเคน:401   ผู้ยื่นคนอื่น:200   <- ได้เนื้อไฟล์
GET /uploads/root2.txt        ไม่มีโทเคน:401   ผู้ยื่นคนอื่น:200
```

`car/` คือเอกสารที่เกษตรกรยื่นตอบข้อบกพร่องหลังถูกตรวจพบ `audits/` คือภาพถ่ายหลักฐาน
การตรวจแปลง ทั้งสองเป็นข้อมูลส่วนบุคคลที่ไม่มีผู้บริโภคสาธารณะ (ต่างจากผลแล็บ ซึ่งหน้า
ตรวจสอบของผู้บริโภคลิงก์ถึง)

`authorizeUploadsObject` รองรับครบทั้ง 5 ชนิดอยู่แล้ว และ fail closed ด้วย
`OWNER_UNRESOLVED` เมื่อหาเจ้าของไม่ได้ · ช่องว่างอยู่ที่จุดเดียว: **ไม่มีใครส่ง 3 ชนิด
ที่เหลือเข้าไปให้มันตัดสิน** การแก้จึงเป็นการเปลี่ยนเงื่อนไขจากรายชื่อ prefix เป็นคำตอบ
ของ `classifyUploadsPath` เอง — ตัวเดียวกับที่ตัดสินว่าอะไรต้องมีเซสชัน ทำให้สองประตู
ไม่มีทางเห็นไม่ตรงกันอีก

**หลังแก้:**
```
/uploads/car/secret.txt   ไม่มีโทเคน:401   ผู้ยื่นคนอื่น:404
/uploads/root2.txt        ไม่มีโทเคน:401   ผู้ยื่นคนอื่น:404
เอกสารของเจ้าของเอง        เจ้าของ:200                        (ไม่มีการเสียการเข้าถึง)
```
เฝ้าโดย `__tests__/unit/every-sensitive-upload-is-decided-by-ownership.test.js` —
ขับ middleware ตัวจริง ไม่ใช่ grep ข้อความ · **พิสูจน์ว่าแดงได้:** ย้อนโค้ดกลับเป็นรายชื่อ
prefix แบบเดิม → แดง 7 ตัวจาก 17 · คืนโค้ดที่แก้ → เขียวครบ

## ✅ ทดสอบแล้วป้องกันได้ถูกต้อง

**IDOR / BOLA** — สมัครผู้ยื่นคนที่สอง แล้วลองอ่านของคนแรก:
```
/api/applications/:id           404      (ไม่ใช่ 403 — ถูกต้อง 403 จะยืนยันว่าแถวมีอยู่)
/api/fees/:id                   404
/api/applications/:id/documents 404
/api/applications/:id/history   404
```

**ไฟล์ที่อัปโหลด — เฉพาะเอกสารร่าง** (`application-drafts/`) ของผู้ยื่น A:
```
ไม่มีโทเคน       401
ผู้ยื่น B (คนอื่น) 404
ผู้ยื่น A (เจ้าของ) 200
```
> รอบแรกผมเขียนบรรทัดนี้ว่า "ไฟล์ที่อัปโหลด" เฉย ๆ แล้วสรุปว่า A01 ป้องกันได้ครบ ทั้งที่
> ยิงทดสอบชนิดเดียวจาก 5 ชนิด · อีก 3 ชนิดคือ SEC-07 ข้างบน — การอ่านรายชื่อชนิดจาก
> โค้ดแล้วยิงให้ครบทุกชนิด คือสิ่งที่พบมัน

**ยกระดับสิทธิ์** — โทเคนผู้ยื่นยิงประตูเจ้าหน้าที่ → 401 ทุกเส้นทาง (คนละ secret)
โทเคนฝ่ายบัญชียิง `/api/admin/users` และ `/api/audits` → 403

**ปลอมโทเคน** — `alg=none` พร้อม `role: admin` → 401 · ลายเซ็นถูกแก้ → 401

**เดารหัสผ่าน** — ผิด 4 ครั้ง → 401 · ครั้งที่ 5 เป็นต้นไป → `423 ACCOUNT_LOCKED`
และรหัสที่ถูกต้องก็เข้าไม่ได้ระหว่างถูกล็อก

**PII ใน log** — ค้นเลขบัตร 13 หลักของผู้ใช้ทดสอบในไฟล์ log ทั้งไฟล์: ไม่พบ

**Error leakage** — ยิงพาธที่มี null byte พร้อมโทเคนพัง: ไม่มี stack trace
ไม่มีพาธภายในเครื่อง

**PII ที่ฝ่ายบัญชีเห็น** — `/api/provider/applications` คืน 13 ฟิลด์ ไม่มีเลขบัตร
เบอร์ ที่อยู่ หรือ formData

**ประตูตรวจใบรับรองสาธารณะ** — ปิดนามสกุลเหลืออักษรเดียวโดยตั้งใจ (มีคอมเมนต์อธิบาย)
เลขใบรับรองไม่เรียงลำดับ ตอบ `valid:false` พร้อมเหตุผลโดยไม่รั่วข้อมูล

## หมายเหตุเรื่องวิธี

SEC-01 ถึง SEC-05 มาจากการยิงระบบจริงล้วน ๆ · SEC-06 และ SEC-07 มาจากการกวาดโค้ด
เพื่อหา "ที่ที่บังคับเซสชัน แต่ไม่ได้ถามว่าเซสชันของใคร" แล้วยิงยืนยันทุกข้อบนระบบที่รันอยู่
ก่อนจะเขียนลงที่นี่ — ไม่มีข้อไหนในไฟล์นี้ที่มาจากการอ่านโค้ดแล้วเดาอย่างเดียว

บทเรียนของรอบนี้: การยิงทดสอบเป็นตัวอย่าง (ลองอ่านเอกสารของคนอื่นสักไฟล์) ตอบได้แค่ว่า
"ไฟล์นั้นถูกป้องกัน" ไม่ได้ตอบว่า "ไฟล์ทุกชนิดถูกป้องกัน" · รายชื่อสิ่งที่ต้องยิงต้องมาจาก
โค้ดที่จัดหมวดเอง (ที่นี่คือ `classifyUploadsPath` ซึ่งบอกอยู่แล้วว่ามี 5 ชนิด)
